# Day 1, Lab 1.4: Store Decision

| Case | Store | Why | Rejected alternative |
|---|---|---|---|
| **A** Daily sales dashboard | Warehouse | The ERP data is fully structured, it refreshes once a day, and the only users are BI analysts. A warehouse is built for BI reporting and dimensional modeling, and analysts can query it with T-SQL without needing Spark. | A lakehouse could technically work since it uses the same SQL engine and Delta format on OneLake, but the data is already structured so it would just be extra setup and file management for data that is already clean tables going to a dashboard. |
| **B** Clickstream plus orders | Lakehouse | The clickstream is semi-structured and the orders and products are structured, and a lakehouse handles both those things. Data science needs the raw events, and Spark is the main tool there. It also fits the Bronze/Silver/Gold setup, where raw data lands first and gets refined in layers. | A warehouse handles structured data, so the raw clickstream would have an extra step before it lands. That throws away the raw detail data science needs and means the transformation happens before we can even keep the original data. |
| **C** Fraud detection | Lakehouse | The events are streaming JSON, which is semi-structured, and the Machine Learning users need to work with the event data directly. A lakehouse handles that and is built for data science. Only 90 days need to stay hot, so this is about handling fast, messy events and not deep history. | A warehouse takes structured data, so the JSON would have to be reshaped first, and loading once a night means fraud would be found hours after it happened. The requirement is seconds, so it fails on speed even before the data shape problem. |
| **D** Regulatory finance | Warehouse | The finance data is highly structured, it's kept for 10 years, and auditors will check it. A warehouse enforces structure, and it supports multi-table transactions, so related tables can be loaded together and stay consistent. | A Data lake has weaker structure and control for data that gets audited. A lakehouse doesn't support multi-table transactions, so a load could leave related tables out of sync. |
